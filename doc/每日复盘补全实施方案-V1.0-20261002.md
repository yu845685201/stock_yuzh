## 一、背景与已确认决策

本方案是"每日复盘系统"的补全实施计划。系统现状（2026-10-02 核实）：数据采集编排（`sync-review-all`，13 日频源 + 2 周频源）、分析链（`daily_review` 8 模块）、六维复盘报告（`review generate`）均已建成并在实战运行；日K 1690 万行（1990 年起全历史）、THS 财报 34.6 万行、申万一级 + 新浪概念成分映射齐备。

**已确认的决策约束（实施时必须遵守）：**

1. **持仓/自选维暂缓**——不做输入机制与报告章节，市场侧数据已就绪，将来启用只需定格式 + 加章节；
2. **不从东方财富采集任何数据**；
3. **封板时间类指标不依赖 1 分钟K线**——采用分笔成交自算方案（开发项 F）；
4. 同花顺 hexin-v 相关路径为红线（项目既有结论，`data_sources/ths_source.py` 探路记录）；
5. 数据真实性原则（CLAUDE.md）：缺数据如实标注"待补"，禁止编造；无法计算的留空。

### 4.1 开发项 A：估值 as-of 取数修复 + PE/PB 历史回填

**前置依赖（V1.2 新增，硬前置）**：**开发项 K（披露日历史回补，§4.11）完成前禁止跑历史回填**——实测 `base_financial_report` 披露日覆盖率 2020~2025 期次为 **0%**（2026 期次 43.3%），as-of 过滤条件 `disclosure_date IS NOT NULL AND <= as_of` 会把历史财报全部筛空，回填产出大面积空值。K 完成后此处放行。

**现状与差距**

`sync/valuation_calc_manager.py` 的 `execute()`（:35）取数固定为"当前时点"语义：

- `fetch_recent_financial_reports(8)`（`dao_review_sync.py:474`）：每只股票**最近** 8 期财报（按 stat_date 排序，无披露日期过滤）；
- `fetch_latest_total_shares()`（`dao_review_sync.py:485`）：**最新**披露总股本。

对当日估值正确；但回填历史日期时会使用**目标日之后才披露**的财报与股本（前视偏差），历史 PE/PB 序列失真，分位统计不可用。

**设计方案**

1. DAO 新增两个 as-of 方法（`dao_review_sync.py`，放在现有两个方法旁边）：

```python
def fetch_financial_reports_asof(self, as_of: str, periods: int = 8) -> List[Dict[str, Any]]:
    """每只股票在 as_of 日已披露的最近 N 期财报（点时口径，估值历史回填用）。

    过滤 disclosure_date IS NOT NULL AND disclosure_date <= as_of；
    ROW_NUMBER 按 stat_date DESC 取前 N（与 fetch_recent_financial_reports 同构）。
    """

def fetch_total_shares_asof(self, as_of: str) -> Dict[str, float]:
    """每只股票在 as_of 日已披露的最新总股本（disclosure_date <= as_of，
    DISTINCT ON ts_code ORDER BY disclosure_date DESC, stat_date DESC）。"""
```

2. `ValuationCalcManager.execute()` 增加回填分支：

```python
def execute(self, trade_date=None, dry_run=False,
            start_date=None, end_date=None) -> Dict[str, Any]:
    # 单日模式（现有逻辑保留）：trade_date 缺省当日
    #   取数改用 as-of 方法（对当日而言 as-of=当日，行为等价、口径统一）
    # 回填模式：start_date/end_date 都给出时，按 base_trade_calendar 交易日循环单日模式：
    #   - 每日: snapshot=fetch_day_kline_snapshot(t)（该日无行则跳过并计数）
    #   - 断点续跑: 已有该日行数 >= 当日K线行数 × 0.8 视为完成，跳过（幂等，可中断重跑）
    #   - 进度: 每 50 日输出一行日志（已回填/总计/预计剩余）
```

3. CLI：`calc-stock-valuation` 增加 `--start-date / --end-date` 选项（`cli/review_sync_cli.py` 的 `calc_stock_valuation`），传入 manager。

**吞吐实测（第四轮 T9）**：单日快照 0.1s + 计算 2.8s + upsert 5,554 行 0.3s（约 2.1 万行/s）→ **5 年回填 ≈ 1.0 小时**（与预估吻合，写入不是瓶颈）。

**口径说明（写入回填报告）**

- 总市值 = 当日收盘（前复权）× 当日已披露总股本。注意：前复权价 × 现股本在除权日附近与真实市值有偏差，**分位统计用途下可接受**（同一股票时间序列自洽），报告注明；
- PE(TTM) 分子分母均点时：分子用 as-of 股本，分母用 as-of 已披露的近四季净利（`_ttm_frame` 逻辑不变，输入换成 as-of 报表即可）；
- TTM 需要"上年年报 + 上年同期"，8 期窗口在 as-of 过滤后个别股票可能不足——`insufficient_note` 留空字段，不硬造（沿用现有 compute 逻辑）。

**测试要求**

- `test_valuation_calc.py` 增补：构造两只股票、两期财报（披露日期跨越 as_of），验证 as-of 取数只含已披露期；回填模式断点续跑的跳过逻辑。

**验收口径**

1. `calc-stock-valuation --start-date 20210101 --end-date 20260930` 跑完，`stock_valuation_daily` 行数 ≈ 区间交易日 × 当日股票数（±10%，停牌因素）；
2. 抽 3 个历史日期（如 20220630、20240131、20250630），人工核对某只大盘股（如 600519）PE = 当日收盘 × as-of 股本 ÷ 当时已披露 TTM 净利，与外部行情软件历史 PE 误差 < 5%；
3. 当日模式回归：跑当日，结果与改造前一致（as-of=当日时行为等价）。

### 4.2 开发项 B：情绪指标日频表 + 回填 + 判据校准

**现状与差距**

报告层 `review/cross_section.py` 的 `sentiment_metrics(cs_today, cs_prev)`（:190）已输出当日全部情绪聚合指标（涨停/跌停/炸板/炸板率/连板梯队/空间高度/溢价均值中位数/晋级率），但每次报告生成都临时重算 60 日面板，且**没有历史序列**——判据阈值（config `review.sentiment_rules`，试用版占位值）无法用历史数据校准；skill 路径的大模型解读也没有时间轴上下文。

**设计方案**

1. **新表** `sentiment_metrics_daily`（DDL 加入 `_REVIEW_TABLE_DDL`）：

```sql
CREATE TABLE IF NOT EXISTS sentiment_metrics_daily (
    id BIGSERIAL PRIMARY KEY,
    trade_date VARCHAR(8) NOT NULL,
    stock_count INT,
    up_count INT, down_count INT, flat_count INT,
    limit_up_count INT, limit_down_count INT,
    burst_count INT, burst_rate NUMERIC(6, 4),
    max_streak INT, ladder JSONB,
    premium_mean NUMERIC(8, 2), premium_median NUMERIC(8, 2),
    premium_count INT, premium_continued INT,
    promotion JSONB,
    sentiment_stage VARCHAR(16),      -- 校准后回填的定位结论（可空）
    rules_version VARCHAR(16),        -- 定位所用规则版本（可空）
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (trade_date)
)
```

字段与 `sentiment_metrics()` 返回键一一对应（ladder/promotion 存 JSONB），另加涨跌平家数（同一截面顺手计算，供大盘环境与 LLM 上下文复用）。

### 4.3 开发项 C：龙虎榜/两融回填循环参数

### 4.6 开发项 F：分笔封板指标（首封时间/开板次数，不依赖 1 分钟K线）

**现状与差距**：打板复盘的核心指标（首次封板时刻、开板次数）缺失；1 分钟K线被排除；东财被排除。**替代方案**：`sync/money_flow_manager.py` 每日已为异动子集（涨停∪跌停∪±7%∪Top50，**涨停股按定义全部在内**）拉取 tdx-api 分笔成交（`_fetch_trades`，:234），同一批分笔可直接派生封板指标，**零额外请求**。

**设计方案**

1. **新表** `limit_seal_stats_daily`（DDL 加入 `_REVIEW_TABLE_DDL`）：

```sql
CREATE TABLE IF NOT EXISTS limit_seal_stats_daily (
    id BIGSERIAL PRIMARY KEY,
    trade_date VARCHAR(8) NOT NULL,
    ts_code VARCHAR(20) NOT NULL,
    limit_price NUMERIC(12, 4),       -- 分笔最大成交价（=当日真实涨停价，见下）
    first_seal_time VARCHAR(8),       -- hhmmss 首次封板
    last_seal_time VARCHAR(8),        -- hhmmss 最后一次封板起算时刻
    open_count INT,                   -- 开板次数（封住→打开的转换次数）
    sealed_ratio NUMERIC(6, 4),       -- 封板时段分笔笔数占比（封板时长近似）
    source VARCHAR(20) DEFAULT 'tdx_tick',
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (trade_date, ts_code)
)
```

2. **计算口径（关键设计：绕开复权陷阱）**：

   - 日K的 `preclose` 是前复权口径，而分笔价格是真实成交价——**直接用昨推算涨停价会错**。方案：对当日涨停/炸板/跌停股，`limit_price = max(分笔成交价)`（A 股成交价不可能超过涨停价，触板即有成交，故最大成交价 = 真实涨停价；跌停对称取 min）；
   - `sealed = (分笔价 == limit_price)`；`first_seal_time` = 首个 sealed 分笔时刻；`open_count` = sealed→非 sealed 的转换次数；`last_seal_time` = 最后一段连续 sealed 的首笔时刻；
   - **封板时段过滤（第七轮 T22）**：分笔按 `09:25~15:00` 截断——北交所存在 15:00 后盘后笔（实测三元基因末笔 15:30、价格为收盘价），不截断会稀释 `sealed_ratio`、影响 `open_count`；`Time` 为 ISO8601 带时区格式（如 `2026-09-30T09:25:00+08:00`，作者复测确认），解析时注意；
   - 分笔含 `Time` 时间戳字段（探路 3.2.4 已实测确认），本项可行性成立；
   - **⚠ 浮点舍入红线（第四轮实算发现）**：任何"理论涨停价"对照必须用 `Decimal ROUND_HALF_UP`——实测江南化工 preclose=4.85：交易所涨停价 5.34（十进制 5.335 四舍五入），Python float `round(4.85*1.1, 2)` = 5.33（浮点存储 5.33499…）；**sealed 判定坚持"分笔 max = 涨停价"口径**（实测分笔 max=5.34 与交易所一致）——该设计同时绕开复权与浮点双重陷阱，不要改成理论价口径；
   - 计算对象 = 日K判定为涨停/炸板/跌停的股票（判定口径沿用 `limit_up_rules`，分笔只提供时间维度）。

3. **接入点**：`MoneyFlowManager._process_stock`（:218）在 `compute_money_flow` 旁追加 `_compute_seal_stats(trades)`，两表同事务写入；当日失败次日历史路径补抓时同样生效（复用现有补偿机制）。

4. **报告接入**：涨停明细、炸板明细表加"首封 / 开板"两列（`sections/stock_movers.py`），无行显示"—"。

5. **历史回补（V1.1 升级：探路实证分笔深度 8 年+，600519 自 2016-11-10 完整）**：
   - 回补子集独立计算：当日 `涨停 ∪ 炸板 ∪ 跌停`（**注意炸板股涨幅可 <7%**，不在 money_flow 现行子集内）；
   - 新增回补命令 `sync-seal-stats --start-date 20251001 --end-date 20260930`：逐日选子集 → 逐股取分笔（含下述重试）→ 计算 → upsert；断点续跑跳过已有行；
   - 回补量估算：250 交易日 × ~90 只/日 ≈ 2.2 万次请求，0.15s 间隔 + 单次 1~3s ≈ 8~12 小时，**分 2~3 晚执行**；更早区间按需扩展；
   - **日常增量同步**：money_flow 子集规则扩为 `涨停 ∪ 跌停 ∪ 炸板 ∪ |涨跌幅|≥7% ∪ Top50`（config 加 `review_sync.money_flow.include_burst: true`，约 +20 只/日），保证日常路径封板指标对炸板股全覆盖。

6. **暂时性错误重试（V1.1 引入 X-4，V1.2 并入 X-9；历史回补的前置）**：
   - **X-4 预热**：探路实测历史日期首次请求超时/空响应、**重试即得全量**（中间件按需预热，Go 侧单请求 2s 超时；注意 `_request` 内置的 3 次通用重试只覆盖"异常"，预热失败表现为**合法的空数据响应**，不会触发）；
   - **X-9 上游断连**：tdx 中间件上游长连接空闲断开（报 `use of closed network connection`），~1 分钟自愈——批量回补必然遇到；
   - 设计：`_fetch_trades`（`money_flow_manager.py:234`）历史日期分支，以下情形均按暂时性错误处理——超时 / **空结果**（X-4）/ 异常消息含 `closed network connection`（X-9，等待 30~60s）——重试 1~2 次（间隔 2s/5s；X-9 类等待 30~60s）后再判定失败；

- `base_financial_report` 共 34.6 万行，**有 disclosure_date 仅 1.3%**：2026 期次 43.3%，**2020~2025 各年期次全部为 0**（比第二轮探路汇总更严重——历史期次接近全缺）；
- 披露日两路来源现状：`base_disclosure_calendar` 仅 2026 年（沪 6952 / 深 9）；`announcement_daily` 仅 20260928 起滚动窗口；
- 后果：A 项 as-of 过滤 `disclosure_date IS NOT NULL AND <= as_of` 会把 2021~2025 历史财报全部筛空，5 年估值回填无法产出；
- **量化坐实（第三轮 T4，作者独立复现一致）**：as-of 20240628 口径下，现状可算 PE 的股票 **0 只（0.0%）**，理想口径（忽略披露日、stat_date < as_of 且 ≥8 期）**5,493 只（98.3%）**——不回补则 A 项历史回填产出为零，回补后 98.3% 可算；
- 财报数值本身完整（1988~2026 全历史，2021~2025 每年约 2.1 万行），缺的只是披露日一列；股本侧 `base_fundamentals_info` 披露日 100% 覆盖，不受影响。

**回补路径（两路均由本方案作者实跑验证，2026-10-02）**

| 路径 | 覆盖 | 实测证据 | 开发量 |
|---|---|---|---|
| ① 沪市预约披露（现有 `sync-disclosure-calendar --year`） | 沪市 | `--year 2021 --dry-run` 实跑：**7882 行（预约 7882 / 实际 7875，99.9%）** | **零**（现有命令） |
| ② 巨潮定期报告检索（现有 `sync-announcement` 扩展） | 沪深北 | 独立探针实跑：全市场窗口 + `category_ndbg_szsh` 过滤生效（2022-04-19~20 两日 645 条 vs 无过滤 12634 条），行含 secCode/secName/announcementTime/标题（"2021年年度报告"等，与现有标题分类词表匹配） | `query_market_window` 加 `category` 参数（镜像现有 `searchkey` 模式）+ CLI 回补选项 |

**设计方案**

1. **沪市（路径①）**：`sync-disclosure-calendar --year 2021`（逐年至 2025，共 20 请求，分钟级）→ `base_disclosure_calendar` 补齐沪市历年预约+实际；
2. **深市/沪深（路径②）**：`sync-announcement` 加回补选项 `--start-date/--end-date --category periodic`：
   - `cninfo_source.query_market_window` / `_query_market_window` 加 `category` 参数（默认空串行为不变；periodic = `PERIODIC_CATEGORIES` 四类常量，已存在）；
   - 按周（7 天）切窗遍历 `20210101~20260930`（年报季高峰周约 2200 条 ≈ 74 页 ≤ 上限 80；超限窗口复用现有 `CninfoWindowTooLarge` 对半拆分递归）；
   - 行映射复用 `announcement_manager._to_announcement_row`（标题分类 → "定期报告"，与 COALESCE 的 `ann_type IN ('定期报告','业绩快报')` 匹配）；
   - **不推进公告游标**（回补语义；`sync_cursor announcement` 属增量，显式区间模式跳过推进）；
   - **seDate 格式红线（第六轮 T18 实测踩坑）**：必须 `yyyy-MM-dd`（isoformat）——传 `yyyyMMdd` 巨潮**不报错、静默返回 0 条**（生产代码已用 isoformat，回补工具沿用）；
   - **必须带 category 过滤**：无 category 时单日全市场 1,787~2,703 条触发 `CninfoWindowTooLarge`；过滤后普通披露日 52~63 条（1~3 页）、截止日单日 1,909 条（64 页 ≤ 上限，作者实测）；**非披露季周仍有 ~32 条/周分散披露（作者实测 2022-06-13~17）→ 窗口必须覆盖全区间，不能只抓披露季**；
   - **请求量裁定（两轮估算冲突，以实测密度为准）**：总量约 15~20 万条（4 类 × 5 年 × ~5000 股 × 正文/摘要）÷ 30 条/页 ≈ **5,000~7,000 请求，0.5s 间隔约 2~4 小时**——第六轮 T18 估算的 400~800 偏低一个量级（按窗口数而非页数计），幂等可重跑、以实际抓取计数为准；风控走既有 `CninfoBlockedError` 冷却；
3. **COALESCE 回填**：回补完成后直接调用现有 `db.backfill_financial_disclosure_dates()`（`dao_review_sync.py:433`，公告 ann_date 优先 / 官网 actual 兜底）——该步骤日常由 ths_finance 同步自动触发，K 工具内显式调用一次确保即时生效；
4. **已知局限（如实标注）**：业绩快报（category_yjkb）不采集——深市历史快报日缺失时 COALESCE 回退到定期报告披露日，as-of 口径略保守（可接受，不硬造）。

**测试要求**：`test_review_sources_parse.py` 增补 category 参数透传用例；`test_review_sync_all.py` 增补"显式区间不推进游标"用例。

**验收口径**
1. 回补后 `base_financial_report` 2021~2025 各期次披露日覆盖率 **≥95%**（沪市由 ① 达 99%+，深市由 ② 公告日覆盖）；
2. 抽 10 只股票 × 随机报告期，披露日与公开信息（巨潮/交易所官网）一致；
3. 本验收 1、2 通过是 A 项历史回填的放行条件。

**预估**：1 人日（路径②开发 + COALESCE 调用；路径①零开发）。

### 4.13 开发项 M：code6_to_ts_code 前缀修复 + 全表名称清洗（X-15/X-17，存量 bug；Phase A 开发启动前先修）

**测试要求**：`code6_to_ts_code` 单测覆盖 5/10/11 开头与既有全部码段；清洗 SQL 先以 SELECT 计数干跑核对（应 = 2,135）。
