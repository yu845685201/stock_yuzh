## 二、执行过程中发现并解决的两个问题

### 问题 1：沙箱 HTTP_PROXY 劫持本地请求（已解决）

环境注入了 `HTTP_PROXY=http://127.0.0.1:58835`，导致访问本地 `127.0.0.1:8080` 的 tdx-api 也被强制走代理，代理不稳定报：

```
ProxyError('Unable to connect to proxy', RemoteDisconnected(...))
```

首轮运行 80 秒内出现 **127 条 ProxyError**。

**修复**：运行时设置 `NO_PROXY=127.0.0.1,localhost`（`no_proxy` 同设），绕过代理直连。修复后 ProxyError 归零。

> 这是环境层面的坑：本机所有调用 tdx-api（127.0.0.1:8080）的脚本都需要带 `NO_PROXY`，否则会间歇性大面积失败。

### 问题 2：区间模式强制全量拉取，压垮 tdx-api（核心问题）

`sync_manager.py:348`：

```python
fetch_full = init_mode or bool(start_date and end_date)
```

只要传了起止日期（哪怕只补 1 天），就会走 **双全量拉取** `get_kline_qfq_full` + `get_kline_raw_full`，每只股返回**约 1 MB** 全历史。8 并发 × 5537 只 × 双源 ≈ 11000 个大响应，服务出现大量瞬时断连：

```
('Connection aborted.', RemoteDisconnected('Remote end closed connection without response'))
```

标准区间路径运行 3m22s 即累积 **81 次"重试耗尽"**（覆盖 138 只股且持续增长），继续跑会产生大量空洞，已终止。

**实测对比（并发 8 / 16）**：

| 接口 | 响应大小 | 结果 |
| --- | --- | --- |
| `/api/kline-qfq`（全量，无 limit） | ~1 MB | 大量 000 瞬时断连 |
| `/api/kline-qfq?limit=8` | ~850 B | 短突发 16/16 全 200 |
| `/api/kline-recent?limit=8` | ~95 B | 短突发 16/16 全 200，最快 0.001s |

**结论**：补齐最近 N 天，正确路径是 tail 接口，而非全量接口。

## 三、最终执行方案

改用 **tail 快速路径**，同时完整复用标准流水线的处理组件，保证数据口径一致：

```
get_kline_qfq_tail(code, 8) + get_kline_raw_tail(code, 8)
  -> _merge_kline_day_sources()
  -> _normalize_kline_day_records(allowed_dates={'20260909','20260910'})
  -> upsert_his_kline_day()   # 按 (ts_code, trade_date) 幂等覆盖
```

参数：并发 8，`tail_limit=8`（足够覆盖 2 个交易日并留缓冲），`adjust_flag=2`（前复权）。

## 五、结论

1. **9-09、9-10 两天数据已补齐且完整**：覆盖 5190 / 5188，与相邻交易日基线（5152）持平略高；抽查 600000 的 amount ≈ volume × price，数据合理。
2. **本次有效耗时 5 分 33 秒**（tail 路径）。作为对照，标准区间路径（全量拉取）不仅更慢，且在当前服务承载下会产生大量空洞。
3. **写入语义为幂等 upsert**：按 `(ts_code, trade_date)` 冲突覆盖，重复采集不产生重复行、不影响其他日期（详见 9-10 的写入语义确认）。

## 六、后续建议

1. **优化 `fetch_full` 判定**：当请求的日期区间落在"最近 N 个交易日"内时，应走 tail 而非 full。这能让"补最近几天"从 18 分钟级降到秒/分钟级，且避免压垮服务。这是当前最大的一处可优化点。
2. **为本地调用统一注入 `NO_PROXY`**：建议在运行脚本/文档中固化，避免代理导致的大面积间歇失败。
3. tdx-api 容器 `tdx-stock-web` 的 SQLite 缓存已通过 bind mount 持久化到 `tdx-api/web/data/database`，重启不会丢缓存，必要时可安全重启。
