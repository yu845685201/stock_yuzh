# 数据采集链路耗时优化方案 V1.0

> 日期：2026-11-19 深夜
> 依据：20261119 采集实测（总墙钟 154 分钟，正常基线约 35 分钟，4.5 倍）
> 范围：`backend/src/sync/` 采集链路 + `config/config.yaml` 调度参数；不含 tdx-api 中间件上游修复（列协作项）

---

## 0. 实测数据（方案依据）

| 阶段 | 耗时 | 构成 |
|---|---|---|
| 前置诊断 | 17 分 | dry-run 中断 + 查库（人工操作，非程序问题） |
| 日K 4 轮 | 78.9 分 | 股票主体合计仅 7.8 分；**raw 兜底恢复合计约 62 分** |
| 复盘编排 | 69.2 分 | 关键路径 = 披露日历 2.0 → **龙虎榜 30.1** → **两融 35.6** → ETF份额 1.5 |
| **合计** | **154 分** | 基线约 35 分 |

三个根因（均有代码定位）：

1. **中间件病态 + 兜底机制放大**：tdx-stock-web qfq 接口间歇返回 HTML（`invalid character '<'`）与畸形数据（`total=0 prices=4 dates=1`），300/002 段集中爆发 → 首轮 218 只失败 → 3 轮补跑；每轮的 raw 兜底恢复阶段对 1612~2124 条 open 台账逐条重拉，被同一故障拖到 14~17 分钟。
2. **pipeline 异常分支 bug**：`kline_day_pipeline.py:171` 引用 `local_source_missing`，但该变量 `:179` 才赋值 → qfq 业务异常时 `UnboundLocalError` 逃逸，单股报废（触发 596 次），且未走 raw 降级。
3. **风控急停冷却烧穿串行链**：`blocked_cooldown_seconds=1800`（20261117 600→1800），lhb/margin 首跑即急停 → 冷却 30 分 → 重试又急停。今天 4 次执行（2 源 × 首跑+重试）**成功率 0%**，冷却串行占用关键路径 60 分钟。

---

## 1. 优化项

### P0-1 修复 pipeline 异常分支 UnboundLocalError

- **位置**：`backend/src/sync/kline_day_pipeline.py`
- **现状**：`local_source_missing` 在 `:179` 赋值，但异常分支 `:164-174` 的 return 字面量在 `:171` 已引用 → `except TdxApiUnavailableError` 块自身抛 `UnboundLocalError`，逃逸到 `safe_process_one_stock`（:361）记单股失败。
- **修复**：把 `local_source_missing = {'qfq_empty': 0, 'raw_empty': 0}` 提前到 `:140` 附近（`stock_detection_details` 初始化区），删除 `:179` 的重复赋值。
- **收益**：qfq 业务异常的单股正常进入失败台账（error 字段完整返回），为 P0-2 熔断计数提供输入。
- **测试**：`backend/test/` 新增用例：mock `get_kline_qfq_tail` 抛 `TdxApiUnavailableError(err_type='biz')`，断言返回 dict 完整、无 UnboundLocalError。

### P0-2 biz 类错误纳入日K熔断

- **位置**：`kline_day_pipeline.py:152-163`（F5/F8 熔断计数）、`config/config.yaml:74`（`kline_day_circuit_breaker: 20`）
- **现状**：熔断只计 `err_type == 'conn'`（:155）。今天故障全部是 biz 类，全量轮连续数百次 biz 失败都不熔断，白烧 7.7 分钟逐只撞病态中间件。
- **修复**：新增 biz 计数器 `consecutive_biz_errors`（同一 `ctx`），单独阈值 `circuit_breaker_biz_threshold`（建议 50，biz 有概率性，比 conn 的 20 宽）；触发后同样 `circuit_tripped`，批内剩余股票快速跳过。
- **配置**：`config.yaml` sync 段新增 `kline_day_circuit_breaker_biz: 50`。
- **收益**：病态日全量轮 7.7 分 → 约 1.5 分（前 50 只撞完即熔断中止），失败名单留给探活恢复后补跑。

### P0-3 raw 兜底恢复阶段熔断

- **位置**：`backend/src/sync/sync_manager.py:624-690`（`_recover_raw_fallback`）
- **现状**：对全部 open 台账逐股拉 qfq tail（:653），异常仅 `warning + continue`（:654-656），无熔断。故障日每轮兜底 14~17 分钟 × 4 轮 ≈ 62 分钟，恢复率仅 457/1979。
- **修复**（两选一，建议 b）：
  - a. 阶段前采样探活：连续 3 只 qfq tail 失败即跳过本轮兜底；
  - b. 过程熔断：连续 10 次 `get_kline_qfq_tail` 失败 → 中止本轮，日志明确"中间件病态，兜底中止，open 台账保留 N 条下轮再试"。
- **正确性**：open 台账幂等保留（:629 设计如此），中止不影响数据，下次正常时自动恢复。
- **收益**：故障日兜底 62 分 → <1 分；正常日不变。

### P1-1 风控急停冷却重试剥离出编排关键路径

- **位置**：`backend/src/sync/review_sync_orchestrator.py:272-285`（`_run_source`）、`config/config.yaml:204`（`blocked_cooldown_seconds: 1800`）
- **现状**：急停后原地 `time.sleep(1800)` 再重试一次。lhb/margin 串行链上 = 2×30 分纯等待；今天重试成功率 0%（两源首跑/重试均秒级急停）。
- **修复**（推荐 a）：
  - a. **急停不再原地 sleep**：`blocked` 时直接标"待补（冷却期至 HH:MM）"，把冷却语义交给 P2-1 晚间补跑作业（补跑时刻 ≥ 冷却期自然满足）。`blocked_retry_once` 默认改 False，`blocked_cooldown_seconds` 保留给确需原地重试的场景显式开启。
  - b. 最小改动版：sleep 改 `min(cooldown, 60)`，1800 冷却挪到晚间补跑调度。
- **收益**：编排关键路径 69.2 分 → 约 9 分（disclosure 2.0 + lhb ~3 + margin ~5.6 + etf 1.5，均按首跑即急停计）。
- **风险与对冲**：急停后立即放弃会少一次"分钟级缓解"的重试机会——20261117 改 1800 的依据正是"600s 重试必失败且多暴露一次"，本方案与该结论一致：**问题不在冷却长短，在于重试发生在串行关键路径上**。晚间补跑在冷却期满后重试，暴露次数不增。

### P1-2 预检强化：间歇性故障采样探活

- **位置**：`review_sync_orchestrator.py` F4 预检（`middleware_health_check_enabled: true`，config:211）；日K独立 CLI `run_cli.py sync-kline-day` 无预检
- **现状**：F4 单次探活，且 `--skip-kline` 后请求集不含 tdx 依赖源 → 今天两轮都未拦住病态中间件（间歇性故障单次探活可能恰好命中健康响应）。
- **修复**：
  - 探活改**采样 5 只**（主板/创业板/北交所各取 1~2 只），连续 ≥2 只失败判病态；
  - `sync-kline-day` 直跑路径加同一预检（抽公共函数，`review_common` 或 `source_expectations` 旁）；
  - 判病态动作：不自动重启容器（保守），报告与 CLI 输出明示"中间件病态，建议 `docker restart tdx-stock-web` 后重跑"。
- **收益**：病态日避免烧全量轮；配合 P0-2/P0-3 双保险。

### P2-1 晚间补跑作业固化（cron）

- **背景**：lhb 17:30 后发布、两融 T-1；交易所域深夜风控敏感（今天 22:30~23:35 风控急停）。主编排 16:30 前跑，lhb/margin 大概率"未到发布时间"或风控——**这两个源天然适合晚间补跑**。
- **方案**：cron 固化每日 20:30 `sync-review-data --sources=lhb,margin,etf_scale`（依赖链由编排器自动处理）；主编排对这三源失败即待补，不人工触发补跑。
- **注意**：D01 已接线退出码（0/1/2/3），cron 侧按 3=部分完成记录，不告警。

### P2-2 采集启动时刻前移

- 今天 21:03 人工触发。建议：**16:00~16:30 主编排**（日K+非交易所域源，避免深夜风控窗口），20:30 晚间补跑（P2-1）。日K 15:30 收盘后即可单独跑。

### P3 协作项：tdx-api 中间件上游（超出本仓库）

- 已知缺陷：① qfq 概率性返回 HTML；② 全量/tail 口径不一致（9 月末 4 天 tail 有全量无，20261118 案例 300082）；③ 畸形响应 `total=0 prices=4 dates=1`。
- 建议：中间件侧响应自检（JSON schema + total/len 一致性）→ 坏缓存自动 invalidate + `refresh=1` 回源；探活端点 `/api/health`。
- 本仓库侧的防御即 P0-2/P0-3/P1-2，上游修复前依赖不变。

## 4. 明确不做

- 不自动重启 tdx-stock-web 容器（探活病态时只报告，重启人工决定）。
- 不改同域串行依赖图（lhb→margin→etf_scale 的防风控串行保留，只消除其上的长等待）。
- 不给 biz 异常加自动重试（今天 3 轮补跑证明：病态期间重试无意义，恢复靠探活判定，不靠盲目重试）。
