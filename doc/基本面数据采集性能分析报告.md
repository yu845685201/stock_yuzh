  - 包括深圳主板、创业板（sz.00*, sz.30*）
  - 包括上海主板、科创板（sh.60*, sh.68*）

### 4.2 时间预估

基于平均每只股票51.51秒的采集速度：

| 指标 | 预估值 |
|-----|-------|
| **总耗时（秒）** | 266,774秒 |
| **总耗时（分钟）** | 4,446.2分钟 |
| **总耗时（小时）** | **74.10小时** |
| **总耗时（天）** | 约3.09天 |

⚠️ **重要提示:** 如果按当前串行模式采集全部5,179只股票的1992Q3至今的所有基本面数据，预计需要**约74小时**（约3天）才能完成。

## 5. 性能瓶颈分析

### 5.1 主要耗时来源

1. **API调用延迟**
   - 每只股票需要调用133次Baostock API（每季度1次）
   - 平均每次API调用约0.39秒 (51.51秒 / 133次)
   - API响应时间存在波动

2. **串行处理模式**
   - 当前采用单线程串行处理
   - 未充分利用并发能力
   - 存在大量等待时间

3. **网络I/O**
   - 依赖外部API服务
   - 受网络状况影响

### 5.2 性能差异原因

三只测试股票的耗时差异较大（28.16秒 vs 64.98秒）：
- **可能原因1:** 网络波动导致API响应时间不稳定
- **可能原因2:** Baostock服务端负载变化
- **可能原因3:** 不同股票的数据量差异（虽然都是75条记录）

## 6. 优化建议

### 6.1 并发采集（推荐 ⭐⭐⭐⭐⭐）

**方案:** 使用多线程/多进程并发采集

**优势:**
- 可将总耗时从74小时降低到几小时
- 充分利用CPU和网络带宽
- 最大化吞吐量

**注意事项:**
- Baostock API限流：QPS不超过50
- 建议并发数：10-20个线程/进程
- 预估优化后耗时：**4-7小时**（假设10个并发）

**参考实现:**
- 已有 `backend/src/sync/concurrent_fundamentals_manager.py`
- 可直接使用或参考其实现

### 6.2 增量更新策略（推荐 ⭐⭐⭐⭐⭐）

**方案:** 仅采集最新季度数据

**优势:**
- 首次全量采集后，后续只需更新最新季度
- 每次仅需采集1个季度（vs 133个季度）
- 耗时降低约99%（从51.51秒降到约0.39秒/只）

**适用场景:**
- 日常数据更新
- 定时任务增量同步

**注意事项:**
- 需要维护已采集的季度记录
- 首次仍需全量采集历史数据

### 6.3 分批次执行（推荐 ⭐⭐⭐⭐）

**方案:** 将5,179只股票分成多个批次

**优势:**
- 避免单次运行时间过长
- 降低失败风险
- 便于断点续传

**建议批次大小:**
- 每批500-1000只股票
- 总共分6-11个批次
- 每批次耗时约7-14小时

### 6.4 智能时间范围选择（推荐 ⭐⭐⭐）

**方案:** 根据股票上市时间动态调整采集起始时间

**优势:**
- 避免采集无效时间段
- 减少无用API调用
- 提升整体效率

**实现思路:**
```python
# 从base_stock_info表读取list_date字段
# 仅从上市日期所在季度开始采集
if stock.list_date > '1992-09-30':
    start_year, start_quarter = calculate_from_list_date(stock.list_date)
```

### 6.5 数据缓存与去重（推荐 ⭐⭐⭐）

**方案:** 缓存已采集的数据，避免重复采集

**优势:**
- 支持断点续传
- 失败重试时跳过已成功的部分
- 节省时间和API调用次数

**实现思路:**
- 数据库记录已采集的股票+季度
- 采集前检查是否已存在
- 支持强制重新采集选项

### 6.6 API调用优化（推荐 ⭐⭐）

**方案:** 优化API调用策略

**措施:**
- 使用连接池
- 合理的超时设置
- 失败重试机制
- 请求速率控制（避免触发限流）
