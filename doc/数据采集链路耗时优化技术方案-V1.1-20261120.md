## 2. 运行流程和完成口径

1. 主作业按交易日历确定报告锚定日 T，冻结应采股票与源清单。独立源照常并行，日 K 依赖源沿用已有门控。各源完成时立即保存取数结果、实际业务日和待补原因。
2. 日 K 主体完成后即可评估门控。定向补跑只处理清单中的股票。达到本轮覆盖要求后放行依赖源。门控未过的依赖源记录待补，日 K 修复后重新评估，再补相应派生数据。
3. raw 兜底价格保有来源标记。前复权恢复使用独立作业，按预算读取打开的台账。未恢复的记录进入后续批次。发生价格或质量修订时，按现有闭环设计登记影响分区。
4. 源尚未发布或触发冷却时，主流程保存最早可重试时刻并释放工作线程。补采作业按到期记录执行，结果回写同一业务分区，每次尝试拥有独立作业号。

| 指标 | 起止和分母 | 用途 |
|---|---|---|
| 主流程墙钟 | 正式主作业启动至最终报告和待补交接持久化完成 | 对比用户日常半小时以内的体验。人工诊断单列 |
| 应到数据就绪时间 | 主作业启动至本次截止已应到的必需分区验收通过，并完成所需派生更新 | 同时披露当日股票覆盖、按交易所的源覆盖、允许临时使用的 raw 行数。未齐时显示缺口与最后观测时刻 |
| 前复权恢复延迟 | 按唯一股票和交易日统计从 raw 兜底入库到 qfq 转正的间隔 | 每轮列出期初积压、新增、唯一销账、期末积压及最老账龄，观察延期是否持续扩大 |

## 3. 日 K 采集与故障隔离

### 3.1 修复异常返回并保存可续跑的股票清单

将 `local_source_missing` 初始化移到两路 API 请求之前。单股失败结果携带 `ts_code`、请求阶段（qfq/raw、tail/full）、错误类别和原始错误摘要，累加一次失败。分别覆盖业务错误与连接重试耗尽。保留原有 raw 兜底的交易日、除权和价格校验，qfq 请求抛错时进入缺口处理。[单股处理](../backend/src/sync/kline_day_pipeline.py) · [双源合并和调度](../backend/src/sync/sync_manager.py)

数据库写入模式下，为本次目标范围保存按交易日、市场分组的代码清单。日常、显式日期范围、指定代码使用各自实际请求范围。调度器分批提交，停止某一组后取消尚未开始的任务，收齐所有已在途结果及其除权触发记录，再核对请求清单、已提交业务行和有证据的停牌等豁免。把失败、取消、未提交、目标日缺行分项写入缺口清单。进程中断后按原范围与数据库重新对账，避免遗漏已写库但未汇总的股票。保留现有行数门控，并在报告中展示应到、实到、豁免与仍缺代码。定向补股继承原作业的运行模式与目标日。日常增量补股仍执行除权检测及必要的整股修订，显式区间回补保留原先的接缝校验语义。

### 3.2 分开检查服务可达性与行情可用性

保留已有 `/api/health` 存活检查。11 月 19 日 22:27:34 编排实际通过了这项预检。日 K 再使用真实 qfq tail 请求，选择沪、深、北近期有有效成交且预期已有数据的代表标的，校验日期、价格与返回结构。预检与主体共享请求和超时预算，直接运行日 K 与内置日 K 复用同一实现。尚未到发布时间、个股停牌、日期滞后、响应畸形、连接异常分别留痕。[健康端点](../../tdx-api/web/server_api_extended.go) · [Python 客户端](../backend/src/data_sources/tdx_api_source.py)

| 故障信号 | 调度动作 | 恢复条件 |
|---|---|---|
| 单股异常、已知历史代码长期无数据 | 保留单股缺口或有依据的豁免，其他股票继续 | 对应代码后续取得有效数据，或确认豁免 |
| 同接口、同市场错误集中 | 在最近完成的一组请求上记录失败比例、样本数、错误类别。代表标的复核也失败时暂停该组并继续健康组 | 冷却到期后少量代表标的通过，再定向处理缺口 |
| 多市场已知可用标的同一接口持续失败，或连接层持续不可达 | 复用连接熔断设施并记录受影响范围。qfq 故障仅暂停依赖该能力的任务，独立源继续 | 探测恢复后先放行一小批，成功后续跑其余代码 |

业务熔断先以观察模式记录“本应暂停的分组、时间、后续实际成功数”。用当晚回放和正常交易日校准最小样本、窗口和失败比例后再开启自动暂停。连接熔断继续保留，校验异常分支修复后能正常通知调度器。

### 3.3 中间件并行修复项

首轮在容器日志中出现 451 次 HTTP 请求处理 panic，栈指向同一处 THS 响应解析。对应 Python 日志中可见连接被关闭和重试耗尽。451 按请求尝试计数，138 按最终失败股计数。可用容器日志复核 11-19 北京时间 21:20:46–21:28:30 的请求异常及栈位置。后续补跑阶段没有新增同类 panic，重复扫描耗时另行核算。Go 端应在解析前校验上游状态、响应长度及 JSONP 边界，返回可分类错误。保留既有字段数量校验，只在解析成功后更新缓存。Python 端保留中间件返回的分类与股票代码。验收以合法响应兼容、畸形响应返回可诊断错误、已有有效缓存受保护为准。缓存失效或批量刷新需要独立证据。[上游响应解析](../../tdx-api/extend/spider-ths.go) · [前复权缓存](../../tdx-api/web/qfq_cache.go)

## 4. raw 兜底恢复独立运行

**入口。** 将 `_recover_raw_fallback` 从“每次日 K 结束都扫描全台账”改为单独的恢复步骤。拟增 `recover-kline-raw-fallback`，供主作业完成后的调度和人工续跑共用。线上切换以独立恢复作业成功运行并产出报告为前提。正常全市场、显式日期补采、`--codes` 和一键编排使用相同策略。只导出、`--no-db` 和 dry-run 均无后台恢复写入。[当前调用与恢复循环](../backend/src/sync/sync_manager.py)

**预算和公平性。** 在原台账上增加可空的上次尝试时刻与下次可尝试时刻，旧的打开记录首次运行即可领取。领取时按已到期、最久未尝试优先，同一股票的日期合并为一次 qfq 请求。每批限制股票数、墙钟及单请求超时。达到预算后停止发起新请求，收尾已在途项并保存进度。源可达但目标日期尚未发布的记录单独退避。预算以正常日吞吐和积压增长实测调整，报告列出预算值、实际耗时和退出原因。

**并发与事务。** 用 PostgreSQL 会话级 advisory lock 保证同一数据集只有一个恢复作业，固定连接持锁、结束释放，外部请求期间不开长事务。更新单个业务键时在短事务内锁定并复核台账仍打开、行情行仍是该版本的 `TDXAPI_RAWFB`，然后更新价格、来源和销账状态并提交。主采集和定向补股的写入也同样受版本约束。首次写 raw 行与打开台账共用事务，幂等重写同一条兜底期间保持其首次兜底时间。以领取时的台账版本和行情来源作条件写入，拒绝较早获取的 raw 回写覆盖已验收 qfq。正常路径写回权威 qfq 时同步处置对应台账。迁移时对账存量 raw 行与打开台账，补登缺账并核实已转正行。按实际状态转换计数。网络失败、事务失败或进程退出后，余项仍能重领。修订登记复用现有分区事务入口，并与依赖重算衔接。[现有台账 DAO](../backend/src/database/dao_kline_day.py) · [分区事务 DAO](../backend/src/database/dao_collection_lineage.py)

## 5. 移出冷却等待与晚间补采

### 5.1 按缺口交接

把 `_run_source` 的原地 sleep 改成按源选择“持久化待补”。行业分类、龙虎榜、两融及其他进入该策略的源共用领取器，补采前重新验收分区。龙虎榜和两融当晚出现过 403、404、400。现有 HTTP 基类将多类 4xx 归入 blocked。保留 HTTP 状态、实际域和源适配器判定。明确限流遵守冷却，对参数、路径或发布状态异常分别诊断，并限制尝试次数。[编排逻辑](../backend/src/sync/review_sync_orchestrator.py) · [HTTP 错误分类](../backend/src/data_sources/http_collector_base.py)

| 持久对象 | 关键字段与归属 |
|---|---|
| 既有 `sync_job`、`sync_partition` | 每次执行新建 job，补采填写 `parent_job_id`。分区键沿用 `build_partition_key`，记录目标日、源实际日、覆盖与最近错误。股票代码清单随对应日 K 分区保存，分块持久化并供恢复对账 |
| 拟增 `sync_collection_retry` | 按数据集、源、业务分区唯一，关联原作业、动作（定向补股或补源）、原因、缺口范围、`retry_at`、尝试次数、状态、租约截止和本次领取 token。对到期任务建索引。同一缺口重复登记幂等合并，保留尚未处理的范围 |
| 拟增域冷却记录 | 按配置的共享请求域/资源组保存 `blocked_until`。主流程、手动入口及补采进程共用互斥和冷却，交易所域继续串行，行业分类按其实际数据源独立处理 |

登记分区结果与新待办用同一事务。交接写入失败时主程序明确报告失败，保留原作业范围以便重建。消费端只领取已到期且域冷却已过的任务，用短事务原子领取并发放有时限的租约。外部请求在事务外执行，写业务行、分区验收及确认完成前，在同一事务校验有效 token 和所领缺口版本，失效响应直接丢弃。按已验收范围核销，领取期间新加入的缺口继续待补。过期租约可重领。成功以目标分区已提交并验收为准，提交后进程崩溃时重新核对即可结清。到重试上限后保留缺口和错误，报告提示人工处理。

### 5.2 调度与日期语义

- 主流程候选时间为交易日 16:00–16:30（北京时间）。逐源计算发布时间，未到期记 `NOT_DUE` 并设置首次可采时间。20:30 可作为集中唤醒时刻，之后仍按最早到期时间或定期扫描继续领取，覆盖 22:29 以后产生的缺口及重启后的漏跑。每次调度都复核域冷却。
- 冻结报告锚定日 T，补跑跨零点仍用原 T。龙虎榜按 T 验收，两融以交易日历推得的 T−1 为目标，并按沪深各自实际数据日核对。两融的发布时间落在对应发布日，不能把 T−1 数据日的收盘时刻直接当作应到时刻。行业分类等快照记录实际观察时间。
- ETF 份额按交易所验收。沪市按目标 STAT_DATE 定向补，深市只提供最新快照，须有目标日证据才能记入 T，错过可采窗口的历史分区记录缺口。现有两融和 ETF runner 依赖运行时默认日期，接入到期补采前要显式传递目标与市场。[源预期定义](../backend/src/sync/source_expectations.py) · [两融入口](../backend/src/sync/margin_manager.py) · [ETF 份额入口](../backend/src/sync/etf_scale_manager.py)
- 拟增 `sync-review-pending` 作为一次性领取命令，供定时器及人工恢复共用。沿用编排 CLI 的约定。退出码 0 为本次应执行项均完成或没有到期任务，1 为本次应执行项全部失败或交接失败，2 为参数错误，3 为部分完成。另报“尚未到期、到期未齐、超过截止”三组数量。晚间最后一次验收仍有到期缺口时明确提示。[现有 CLI 退出码](../backend/src/cli/review_sync_cli.py)
