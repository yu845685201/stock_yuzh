# 日 K 线数据采集技术方案 V3.0（中间件增强版）

> 版本：V3.0 | 日期：2026-09-05
> 前序文档：[日K线数据采集技术方案.md](./日K线数据采集技术方案.md)（V2.0，不改中间件基线方案，**继续有效并作为过渡/兜底路径保留**）
> 本方案 = V2.0 的双源双域数据设计 + 方案 C 中间件增强 + 基本面采集修复，目标：日常增量采集降至**分钟级**、基本面时点匹配无未来函数
> 关键接口行为均经实测验证（tdx-api 中间件 + baostock，2026-09-05）

## 1. 与 V2.0 的关系

| | V2.0（基线） | V3.0（本方案） |
|---|---|---|
| 数据设计 | 双源双域（前复权价←同花顺源，amount←通达信原始源） | **完全相同** |
| 三种采集模式 | 全量/区间/增量 | **完全相同** |
| 准确性机制 | 除权检测、原子替换、两源校验 | **完全相同** |
| 中间件 | 不改动，接受每次调用服务端全量拉取（2-8s/股） | **增强**：尾部单请求接口 + K线缓存 + 除权事件失效 |
| 日常增量墙钟 | 40-90 分钟 | **3-5 分钟**（高峰日 ≤8 分钟） |

V2.0 的全部实测结论（接口能力对照、Amount 口径、Last 跨快照除权检测）在本方案中继续成立，不再重复。V2.0 的 P1 阶段实施内容（M1-M4）是本方案的子集——**先按 V2.0 落地跑通，再无缝升级到 V3.0**，采集侧代码通过开关切换数据路径。

## 2. V3.0 的核心问题：为什么必须改中间件

当前中间件对所有日 K 接口的实现都是"服务端向同花顺/通达信**全量拉取**后再截取"：

- 同花顺前复权：每股 2-8 秒，且无法跳过（第三方接口行为）
- 通达信原始：每股 0.5-5 秒（800 条/批 × 11 批拼接），但协议本身支持**单请求取最近 N 条**（约 50-100ms，实测 000001 全量 0.5s ÷ 11 批 ≈ 45ms/批）

即：调用方即使只要最近 2 条，服务端也要付出全量代价。**这是墙钟时间的唯一根源**。V3.0 在中间件侧解决它，同时必须解决一个新引入的问题——**缓存的除权失效**（见 §3.2，这是 V3.0 设计的关键难点）。

范围说明：`/api/kline-history` 的日期参数缺陷同样影响 1 分钟线模块（`kline_1min/usecase.py`、`adapters.py` 走同一接口），其区间行为与修复不在本方案范围，需另行评估。

## 3. 中间件增强设计（tdx-api 仓库，Go）

### 3.1 新增接口：原始日K尾部单请求

```
GET /api/kline-recent?code=000001&type=day&limit=N
```

- 实现：`client.GetKlineDay(code, 0, N)` 单次协议请求（分钟线 handler 已在用同款调用），不走 800 条批拼接
- 返回：最近 N 条**原始**（不复权）K 线，含真实 Amount，响应 <1KB
- 耗时：约 50-100ms/次（对照实测：全量拼接 0.5s = 11 批）
- 此接口独立有用，可先行上线，即使调用方暂不升级也能降低原始域采集成本

### 3.2 前复权序列缓存 + 除权事件失效（本方案核心难点）

**缓存内容**：每股同花顺前复权全量序列。**接入点**：改造 `/api/kline-history` 与 `/api/kline` 的 day 分支为"缓存优先、失效回源"，对外接口路径不变，调用方无感知；week/month 分支由同一 qfq 日线缓存转换生成，一并纳入缓存覆盖。

**缓存载体**：复用中间件已有的本地 K 线库（`data/database/kline`，`/api/tasks/pull-kline` 已在写入；qfq 缓存与原始域数据**分表存储**，防止两域混写），磁盘持久、重启不丢；热点股可加内存层。内存占用估算：5,200+ 股 × 8400 条 × ~70B ≈ 3GB（全内存方案），磁盘方案无此压力，需配置 LRU 淘汰。

**失效难点**：缓存命中时没有新拉的同花顺序列，而除权在原始 K 线里**不可见**（实测：Last 是上一条收盘价的机械回显，除权日也不变），跨快照检测失效——缓存若盲目追加新 bar，会在除权日把断层写进缓存且无人察觉。

**失效机制（主）**：TDX 协议原生支持除权除息信息查询：

```
protocol.KMSG_XDXRINFO = 0x000f   // 协议常量已存在（injoyai/tdx）
```

- 中间件在服务缓存前，向通达信服务器查询该股自缓存锚定日以来的除权除息事件（单次协议请求，约 50ms；事件列表本身可缓存增量更新）。注意只对**除权除息日 ≤ 当前日**的事件触发失效——公告在前、除权在后的"未来事件"不应提前失效缓存，否则公告日至除权日之间每天都会做无谓的同花顺全量重拉
- 有事件 → 缓存失效 → 重新向同花顺全量拉取该股 → 更新缓存锚定日 → 服务
- 无事件 → 从缓存服务尾部，新 bar 按原始值追加（除权未发生时 qfq≡raw，实测近期因子恒为 1）
- 实现风险：协议常量已存在，但客户端封装方法可能需按 TDX 协议格式自行补齐（中等工作量）；这是 V3.0 唯一的技术不确定点

**兜底机制（辅）**：每周一次全市场校准（周末窗口，40-90 分钟），**强制绕过缓存**逐股从同花顺重拉并与缓存比对，不一致即修正并告警——为此缓存接口需支持旁路参数（如 `refresh=1`），否则校准会命中缓存而失去意义。校准把任何漏检导致的失真上限压到一周。

### 3.3 可选增强：原始序列缓存

原始序列**不可变**（只追加、永不改写），是理想缓存对象。缓存后"指定日期区间"模式也降为分钟级。建议作为 M-B2 跟进，非首期必须。

### 3.4 可选增强：聚合接口

`GET /api/kline-day/full?code=X` 与 `GET /api/kline-day/tail?code=X&limit=N`——中间件内存中双域对齐，一次返回 qfq 价 + 真实 amount + volume + raw_close，调用方每股每日仅 1 次调用。首期可不聚合（调用方双请求合并），视 M-B 落地后取舍。

## 4. 采集侧设计（stock_yuzh）

数据模型、三种模式、准确性机制与 V2.0 §5-§7 **完全一致**，仅数据获取路径切换：

| 模式 | V2.0 数据路径 | V3.0 数据路径 |
|------|--------------|--------------|
| 全量初始化 | `/api/kline` + `/api/kline-all`（双全量，2-13s/股） | `/api/kline`（同花顺全量，建 qfq 缓存）+ `/api/kline-all`（原始全量取 amount）；再次初始化 qfq 命中缓存，raw 仍需全量拉取（M-B2 落地后命中缓存） |
| 指定日期区间 | 双全量拉取 + 内存过滤 | qfq 命中缓存；raw 需 `/api/kline-all` 全量拉取（全市场 15-45 分钟）；M-B2 落地后分钟级；未缓存股回退 V2.0 路径 |
| 日常增量 | `/api/kline-history?limit=2` + `/api/kline-all?limit=2`（服务端仍全量，40-90 分钟） | qfq 尾部（缓存）+ `/api/kline-recent`（单请求），**3-5 分钟** |

- 调用方自身的跨快照除权检测（新拉 Last vs 库存 Close）**保留**，降级为三道防线之一：XDXR 失效（主）→ 调用方检测（辅）→ 周度校准（兜底）。**注意**：调用方检测命中后的全量重拉必须带 `refresh=1` 强制绕过缓存回源，否则会从同一份失效缓存取回同样错位的数据，第二道防线形同虚设
- 原始域不可变性校验（fresh raw_close vs 库存 raw_close）保留，检测源数据修订
- 开关：`config.yaml` 增加 `kline_day.use_enhanced_api: true/false`，false 时回退 V2.0 直连路径，保证中间件升级期间采集不中断
- CSV 双落地（`uat/data`、`prod/data`）与 PostgreSQL 并行写入的项目约定保持不变，本方案仅改变数据获取路径，不影响落地层

## 5. 基本面数据采集优化（基本面线）

日K采集在 `_normalize_kline_day_records` 中按 `disclosure_date ≤ trade_date` 匹配最近一期基本面（股本用于换手率，披露日期落库）。排查发现基本面采集实现存在准确性问题，纳入本方案一并解决。

### 5.1 现状问题（实测确认）

| # | 问题 | 根因 | 影响 |
|---|------|------|------|
| 1 | **disclosure_date 不是披露日** | `baostock_source._get_disclosure_date()` 用规则推算"季度末"（0331/0630/0930/1231）冒充披露日，而 baostock `query_profit_data` 响应中本就携带 `pubDate`（真实披露日）与 `statDate`（报告期） | ① **未来函数**：年报报告期 12-31、实际披露多在次年 3-4 月，匹配却从 1 月 1 日即命中，前视最长约 4 个月；② 字段语义与表注释（"财报发布日期"）不符 |
| 2 | **数据滞后** | 基本面采集无自动调度（`sync-fundamentals` 需人工触发），近一年未执行，库中最新报告期停留在 2025Q3（20250930），缺 2025Q4 / 2026Q1 / 2026Q2 三期 | 换手率分母（流通股本）使用约一年前的旧值 |

实测依据：`query_profit_data` 对平安银行 2025Q3 返回 `pubDate=2025-10-25, statDate=2025-09-30`（库中存的是 20250930）；2007Q1 起全部可采（2005Q1 无数据，能力边界与现库 75 个报告期一致）；2026Q2 可采（pubDate=2026-08-15）。

### 5.2 采集方法调整

采集机制不变（仍为 `query_profit_data` 逐股逐季调用，baostock 无全市场批量接口），仅调整字段映射与键语义：

1. `get_financial_data`：动态字段定位加取 `pubDate`、`statDate`（与 totalShare/liqaShare 同款方式），删除 `_get_disclosure_date()` 推算逻辑
2. 真实性原则：pubDate 缺失时 disclosure_date 存 NULL、stat_date 照存并计入异常，不回填推算值（注意：现列有 NOT NULL 约束，需在 5.3 迁移中一并放开）
3. upsert 冲突键改为 `(ts_code, stat_date)`

**baostock 并发约束（重要）**：baostock 不支持并发调用，基本面采集**全程单会话串行**（单会话内亦不可多线程）。现存 `concurrent_fundamentals_manager` 对 baostock 无效，不得用于该数据源；限速沿用现有 rate_limiter。串行约束下的重刷成本见 5.3（实测单次调用 138ms，可接受）。

### 5.3 表结构迁移与全量重刷

**表迁移**（原地、零丢失）：

```sql
ALTER TABLE base_fundamentals_info ADD COLUMN stat_date VARCHAR(8);
UPDATE base_fundamentals_info SET stat_date = disclosure_date;  -- 现值即报告期，平迁
ALTER TABLE base_fundamentals_info ALTER COLUMN disclosure_date DROP NOT NULL;  -- 允许 pubDate 缺失留白
ALTER TABLE base_fundamentals_info DROP CONSTRAINT uk_base_fundamentals_info_code_date;
ALTER TABLE base_fundamentals_info ADD CONSTRAINT uk_bfi_code_stat UNIQUE (ts_code, stat_date);
CREATE INDEX idx_bfi_pub ON base_fundamentals_info (disclosure_date);
```

说明：报告期（一股一期唯一）才是自然键——年报与一季报**同日披露**（4 月底常见）会使 `UNIQUE(ts_code, pubDate)` 冲突；disclosure_date 列保留，语义自此 = 真实披露日。另注：实测库中该列为 VARCHAR(8)（init-V1.sql 写的是 TIMESTAMP，DDL 文档与实际结构不符，随 M 阶段文档同步一并修正），迁移按实际结构执行。

**全量重刷**：

| 项 | 内容 |
|----|------|
| 范围 | 以 `base_stock_info` 股票清单（**type=股票**，含退市股共 5,537 只，`list_date` 可枚举各股上市期）× 各股上市以来全部报告期生成**任务全集**（覆盖存量 225,444 个组合、补缺 2025Q4/2026Q1/2026Q2、并拾回因历史失败而整体缺数的股票），≈ **24-26 万次调用**（pubDate 无法从报告期本地推导，存量必须重拉） |
| 执行方式 | **baostock 单会话串行**，实测 138ms/次 × 24-26 万 ≈ **9-10 小时，一夜窗口**（含重试缓冲 10-12h） |
| 断点续传 | 按股票粒度 checkpoint，中断跳过已完成；upsert 幂等可重跑；失败股重试 3 次后跳过、汇总报告、次夜补跑；跨夜运行需处理 baostock 会话超时（自动重登） |
| 灰度 | 先重刷 100 只代表股（大盘银行/ST/次新股）通过 5.5 验证后再放全量 |
| 日常增量 | 此后按季度常规同步：单季全市场（base_stock_info type=股票，5,200 只）× 138ms ≈ **12 分钟**（串行），披露季（4/8/10 月）各跑一次 |

### 5.4 匹配逻辑微调

`_build_fundamentals_map` 排序键由 `disclosure_date` 改为 `(disclosure_date, stat_date)`：同日披露年报+一季报时，bisect 取报告期更新的一份（股本更新）。`_match_fundamentals` 二分逻辑不变；无 pubDate 的记录不入 map（时点不明不参与时点匹配）。

### 5.5 验证清单

1. 行数守恒：每个 (ts_code, stat_date) 覆盖与迁移前一致（±补齐期数）
2. **前视消除**：随机抽 1000 个（股，交易日），断言匹配记录 pubDate ≤ 交易日
3. 抽样比对：平安银行 2025Q3 应为 2025-10-25（旧值 20250930）
4. 同日双报告：抽 4 月底同日披露年报+一季报的股票，两条记录共存且匹配取 stat_date 更新者
5. turnover_rate 抽样重算一致

### 5.6 对日K表的联动

`his_kline_day` 已存的 `fundamentals_disclosure_date / total_share / float_share` 三列按旧语义（报告期）匹配写入，需重算：**并入 §7 的 M2 日K基线重建**（normalize 时自动使用新匹配，零额外作业，推荐）；若需先行，可跑独立回填作业（纯数据库重匹配，实测库约 **1,665 万行** / 5,218 只，预计 40-90 分钟，不调外部接口）。`change_rate / preclose` 不依赖基本面，不受影响。

另注：§3.2 的 XDXR 除权事件能同时识别送转类股本变动，后续可作为 float_share 季度粒度滞后的补充刷新信号（增强项，不阻塞本方案）。

## 6. 耗时预估（V3.0 达成后）

| 模式 | 首次 | 常态 |
|------|------|------|
| 日常增量（全市场 5,200+ 股，12 并发） | — | **3-5 分钟**；分红高峰日（200-300 股除权）≤8 分钟 |
| 全量初始化 | 40-90 分钟（同花顺逐股建缓存，一次性） | 15-30 分钟（qfq 命中缓存，raw 仍需全量拉取；M-B2 落地后分钟级） |
| 指定日期区间 | — | 15-45 分钟（qfq 命中缓存，raw 需全量拉取）；M-B2 落地后分钟级 |
| 基本面全量重刷（一次性） | 一夜串行（≈24-26 万次 × 138ms ≈ 9-10h） | 季度常规同步：单季 ≈ 12 分钟（5,200 股，串行） |
| 周度校准（运维节奏） | — | 每周一次 ≈ 40-90 分钟（强制绕过缓存的夜间窗口） |

单股成本拆解（增量）：qfq 尾部缓存命中 10-50ms + XDXR 事件校验 ~50ms + 原始尾部单请求 50-100ms + 开销 ≈ **0.2-0.3s**；瓶颈只剩除权日的同花顺重拉（第三方源 2-8s/只，无法优化，但仅作用于每日几十~几百只）。

## 8. 风险与边界（V3.0 新增部分）

| 风险 | 应对 |
|------|------|
| XDXR 客户端封装缺失（常量有、方法可能无） | 提前做协议验证 spike（1-2 天）；不可行则降级为"周度校准 + 调用方检测"双防线，代价是失真窗口上限一周 |
| 缓存内存压力（全内存约 3GB） | 磁盘缓存（复用本地 K 线库）+ LRU，热点内存层按需 |
| 缓存与同花顺源漂移（非除权的数据修订） | 周度校准 + 调用方 raw 不可变性校验 + Last 检测三道防线 |
| 中间件升级期间两套路径行为不一致 | `use_enhanced_api` 开关 + 灰度 + 双路径对账（同一批股票双路径各采一次比对）；注意中间件侧缓存部署后对两条路径同时生效，中间件自身故障的回滚以**镜像回退**为准 |
